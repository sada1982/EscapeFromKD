3. 今回の最適化調査で分かったこと
=================================
要求: 現在約30 FPSの3Fを、最低60 FPS以上へ改善する。
60 FPSのフレーム時間は16.67 ms。GPU時間だけでなくCPU/実フレームを確認する。
今回の3つの有効計測は全て600フレーム。全フレームが16.67 msを超えている。

【有効な計測条件】
UE EditorのフローティングPIE、実習室の同一開始位置、移動・射撃なし。
起動位置(402,-73,100) cm、Yaw -90度、Pitch/Roll 0度。
PIEビューポート1914×994。厳密な1920×1080ではない。
ProfileGPUで確認した内部解像度例1439×748→1914×994。
r.ScreenPercentage=0の自動設定であり、ネイティブ100%比較ではない。
r.DynamicRes.OperationMode=0、r.VSync=0、t.MaxFPS=0。
8～12秒のウォームアップ後600フレーム。取得中はUE/MCP呼出しを行わない。
計測中のみ背景CPU/Slateスロットリングを解除。停止時には復旧済み。
ウィンドウ最小化等で約3 FPSに落ちた試行は無効として除外。
CPU温度・電源・他プロセスは厳密には固定しておらず、別PCへ数値を外挿しない。

・VRAM改善だけで60 FPSになったわけではない。

  44.614 / 45.253 / 44.247 / 44.565 / 44.540 / 44.746 msで安定。

・AnimationというCSV区分は、単にAnimGraph計算だけを意味しない。
  SkeletalMeshのTick・アニメ完了・変形や衝突更新などを含み得る。
  どのActorのどの処理かは、現CSVだけでは確定していない。

4. GPU/VRAMと照明の監査
=======================
RTX3050の4 GB VRAMに対し、BaselineのLocal使用約4056 MB、予算約3368 MB。
赤いVRAM不足メッセージは実際の予算超過。表示を隠すことは性能改善ではない。
主なメモリ使用はRenderTargetPool約2936 MB。
通常テクスチャのwanted約10 MB、non-streaming約87 MBで、
ステージ材質テクスチャの縮小を第一手にしても大幅改善は見込めない。
RT geometry約17.6 MB、DistanceFieldAtlas約8 MB、NaniteRoot約16 MB。

TSR100後のRenderTarget監査で確認:
  VSM PhysicalPagePool 512 MB ×2
  VSM HZB             約85.375 MB ×2
  Lumen Atlas類       64 MB級の複数面と重複
  RadianceCache       72.25/64/32 MBなどの組み合わせが複数
同種資源の二重存在は確認済み。EditorとPIEの両ワールド由来という説明は推定。
VSM4096→2048では2組で約597 MB減る理論見積り。
Memory ABの複合変更では実測Local使用がBaselineから約680 MB減少。

照明:
RectLight42灯 + PointLight4灯。全てMovable。
RectLight42灯は影ON、最大描画距離0（距離制限なし）。
内訳: 開始実習室12、隣接教室9、CAD9、廊下/展示9、吹き抜け1、階段1、EV1。
教室30灯のAttenuationRadiusは450 cm、廊下9灯は330 cm。
吹き抜けPoint3灯は半径1800 cm、階段Point1灯とともに影なし。
全灯がGI/Reflection/Translucencyに影響。
実習室中央を最大16灯の減衰球が包含する上限計算あり。
これは実際に16灯が同時描画されると測定した意味ではない。
Unbound PostProcessは露出Min/Max=6、Bias=0が主な上書き。
今回、照明の位置・数・影・明るさ・PPの保存値は変更していない。

NaniteのGPU内訳例はVisBuffer約0.7 ms、BasePass約1.08 ms。
現状では「三角形を減らせば直ちに60 FPS」とはいえない。
巨大な分類別メッシュでもNaniteのクラスタカリングは働くので、
非表示教室の全三角形が常に描画されるとは断定しない。
詳細はEvidence/LightAudit、Evidence/ModelAudit、Evidence/PerfAuditを参照。

8. 自宅での再開手順（この順序で進める）
=======================================
A. 同じ状態を開く
1) ユーザーがプッシュした最新内容とLFS実体を取得する。
   git status、HEAD、UEバージョン、GPU/VRAM、uprojectのプラグインを確認。
2) 本資料とEvidence/checkpoint_validation.jsonを読む。
   Unreal MCPのツールを再発見し、現在Level/PIE/未保存アセットを読み取り確認。
3) KDStage / You / BP_Floor03 / BP_AdmissionRobot / BP_Rifleと既存設定を確認。
   ユーザーの未保存変更があるなら勝手に保存・破棄しない。
4) 軽量化候補はまだ未採用と確認。先にインポートしない。

B. 最優先: CPU Animation負荷と敵PerPolyCollisionを切り分ける
5) 自宅PCで現状の600フレーム基準を新規測定する。
   カメラ、実表示解像度、内部解像度、品質、電源、PIEモードを記録。
   PIEを前面にし、最小化しない。暖機後、計測中のMCP/UI操作を避ける。
6) PIE中の敵MeshComponentのPerPolyCollision、プロファイル、応答、可視性、
   Tick設定を読み取り記録する。
7) 実在する公開APIを確認して、PIE中の敵MeshComponentだけPerPolyCollisionをOFF。
   SkeletalMeshアセット/CDO、You、Stage、アニメTick、可視性を同時に変更しない。
   SetEnablePerPolyCollision等の名前は利用先のスキーマ/UE APIで実在を確認して使う。
8) 同条件・暖機後600フレームを測定し、GT Animation/GT/Frame/GPU/RT待ちを比較。
   この間は命中精度が変わり得る。実験設定を保存しない。
9) 元のフラグへ戻すかPIEを終了する。
10) 明確に改善したら、CPUトレースで衝突更新等の所有処理を確認し、
    軽量な敵の当たり判定へ置き換える最小案を検討する。
